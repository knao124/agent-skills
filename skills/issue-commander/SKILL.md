# Issue Commander

## 概要

T3 Codeで、1つの親イシューにひもづくサブイシューを、作業単位ごとのトップレベルのスレッドで並行して進める。このskillを使うスレッドは司令塔として、分担、スレッド間の受け渡し、進捗の把握、ユーザーへの相談だけを行う。司令塔はコードを直接編集しない。

## 役割とモデル

ユーザーが別の指定をしない限り、次の割り当てを使う。モデルの名前が変わったときは、この表だけを直す。

| 役割 | providerの`driverKind` | model | options |
|---|---|---|---|
| 司令塔 | `claudeAgent` | `claude-opus-5-5` | なし |
| 設計 | `claudeAgent` | `claude-opus-5-5` | なし |
| 設計レビュー | `codex` | `gpt-6.2-sol` | `[{ "id": "reasoningEffort", "value": "high" }]` |
| 実装 | `codex` | `gpt-6.2-sol` | `[{ "id": "reasoningEffort", "value": "high" }]` |

- 設計、設計レビュー、実装の順に進める。設計レビューは設計を書いたスレッドと別のスレッドに依頼し、読み取りだけでレビューしてもらう。指摘には重要度、該当箇所、修正案を求める。
- レビューには設計の参照先と対象の版を渡す。指摘への対応と採用した方針が決まったら、設計の確定版と残課題を実装スレッドに渡す。実装中に設計変更が必要になった箇所も、この順で進める。
- 割り当てる前に`orchestrator_capabilities`でモデルとオプションを確かめる。短い一覧に見当たらなければ`search`で探す。指定のモデルや設定が使えない場合は、該当する割り当てを保留し、ユーザーに伝える。
- 司令塔のモデルが表と違う場合は、現在のモデルをユーザーに伝える。実行中のターンでモデルを切り替えることはできない。

## 手順

依頼に該当する段階から進める。計画の整理や進捗報告だけを求められた場合は、その結果を会話で返す。

### 1. 親イシューを読み、整理して見せる

1. 親イシューを担当するときは、`link_issue`の`url`に親イシューのURLを渡し、このスレッドに紐づける。
2. 親イシューの本文とコメント、すべてのサブイシュー、本文で参照されている関連イシューとPR、リポジトリの設計書を読む。
3. 次を整理して見せる。
   - 依存関係。並行で進められるもの、他の完了を待つもの
   - 作業単位ごとに触りそうなファイル。既存のファイルと、新規のファイルの候補を分ける
   - 同じファイル、migrationの連番、インフラの定義のように、並行作業で衝突しやすい箇所
   - 設計書より前に作られたPRやコードで、今の設計と合わないもの
   - ユーザーに決めてほしいこと。勧める案と、その理由を添える
4. 新しいトップレベルのスレッドは、ユーザーからスレッド作成の依頼がある場合に立てる。

設計書の構成要素と依存関係に沿って作業単位を決める。1つのサブイシューでも、担当する役割や着手条件が異なる段階は別の作業単位にできる。

### 2. 決定と共通の前提を親イシューに残す

イシューへの書き込みが依頼の範囲に含まれる場合は、ユーザーと決めたことを親イシューのコメントに残す。未コミットの変更は別のworktreeに引き継がれないため、全スレッドで読む決定事項と成果物の参照先を親イシューに集める。

- 作業の整理をまとめるコメントに、決めたこと、作業単位の表、依存関係、進める順番を書く。状況が変わったら同じコメントを更新し、完了した作業単位には完了とPR番号を書く。
- 共通の前提をまとめるコメントに、全スレッドが守る決まりを書く。
  - 担当する作業単位の範囲だけを変更する。範囲外の変更が要りそうなときは、手を付けずに親イシューにコメントする
  - 他のスレッドにも効く決定が出たら、親イシューにコメントする
  - 専用のworktreeと `codex/` で始まるbranchで作業する
  - 連番、共有ファイル、インフラの定義など、衝突しやすいものの割り当て
  - 外部のリソースを作ってよいスレッドを、リソースごとに1つに決める
- サブイシューの本文が決定と食い違ったら、本文を書き換える。レビューで出た指摘のうち後の作業単位で扱うものは、該当するサブイシューにコメントで残す。

### 3. 作業スレッドを立てる

- 担当と着手条件が決まった作業単位ごとに、`t3_thread_launch`でトップレベルのスレッドを1つ立てる。`message`に作業指示を書き、`workspaceStrategy`には`type: "worktree"`と`codex/`で始まる`branch`を指定する。
  - 起点の指定があれば従う。独立した作業は通常、`baseRef`を`origin/<既定のブランチ>`、`startFromOrigin`を`true`にする。リモートがなければローカルの既定ブランチを使い、`startFromOrigin`を`false`にする。
  - 依存先のブランチや未公開のコミットが必要な作業は、ローカルのブランチやコミットを`baseRef`に指定し、`startFromOrigin`を`false`にする。引き継ぐ変更がコミット済みであることを確かめる。
- `modelSelection.instanceId`には、表の`driverKind`に対応する`providerInstanceId`を入れる。`modelSelection.model`と`modelSelection.options`は表に従い、設定がない役割では`options`を省略する。
- 作成後は、`link_issue`に返された`threadId`と担当のサブイシューの`url`を渡す。既存PRを引き継ぐ場合は`link_pull_request`にも`threadId`と`url`を渡す。紐づけたら`t3_thread_read`で起動後の状態を確認する。
- `t3_thread_launch`には作業単位ごとの`clientRequestId`を渡し、起動結果が不明なときは同じ値で再試行して重複起動を防ぐ。
- 最初の指示には、親イシュー、担当のサブイシュー、共通の前提、設計書の参照先を書く。作業範囲、完了条件、必要な確認と、承認済みの外部操作があればその範囲も伝える。用意されたworktreeとブランチで作業してもらい、PRのURLは司令塔に返してもらう。
- 同時に進める本数は、依存関係とレビューできる量を見て決める。3〜4本を目安とし、依存先の成果物がそろった作業から次のスレッドを立てる。

### 4. 進捗を見て、受け渡す

ユーザーに進捗を聞かれたら、各スレッドを`t3_thread_read`で読み、`pull_request_read`でPRのCIを確認する。親イシューとサブイシューの新しいコメントも確かめる。進捗確認だけの依頼では、見つけた停滞と次に必要な対応を報告する。

- 質問で止まっている場合は、`t3_pending_request`の`action: "list"`に`threadId`を指定し、出てきた質問を`action: "read"`と`requestId`で読む。ユーザーの判断が必要な質問は判断材料とともに伝える。
- 別に立てたトップレベルのレビュースレッドの結果は、依頼元に自動では戻らない。`t3_thread_read`で結果を取得し、進行も任されている場合は依頼元に渡す。返事を待ったままターンを終えたスレッドにも、進行に必要な決定を届ける。
- 受け渡しには`t3_thread_send`を使い、`threadId`と`message`を指定する。作業中のスレッドで次のターンに読んでほしい場合は`mode: "queue"`を使う。作業が重複している場合は担当を1つに決め、実行中の作業を止める指示には`mode: "steer"`を使う。
- レビューの指摘のうち今のPRで直すものは担当のスレッドに渡す。後続の作業に回す指摘は、書き込みが依頼の範囲に含まれる場合に該当するサブイシューへ記録する。

進捗の報告は、次の4つの見出しで書く。

1. ステータス。スレッド、状態、PR、CIを表にする。スレッドはT3 Codeが返した`link`の表記をそのまま使う
2. 前回からの差分
3. 課題
4. 相談事項・確認事項。勧める案と理由を添える

### 5. マージして締める

- マージを任されている場合は、依存先の作業、PRの向き先、最新のhead、CIとレビューを確認する。`pull_request_merge`の`expectedHeadSha`には、確認した`summary.headSha`を渡す。
- 積み上げたPRは下のPRからマージする。上のPRは向き先を確認し、必要なら既定のブランチに変更する。差分とCIを再確認してからマージする。
- ユーザーからスレッドを締めるよう依頼されたら、`t3_thread_organize`に`threadId`と`action: "settle"`を指定する。作業の完了は、書き込みが依頼の範囲に含まれる場合に親イシューの表へ反映する。

## 守ること

- 司令塔はコードを編集しない。設計書の修正も、担当のスレッドに任せる。
- 設計書より前に作られたPRやコードは、今の設計に合うかを確かめてから扱う。合わないものは、そのまま使う前提にしない。
- 取り消せない操作、本番への反映、外部への公開、費用が発生する操作は、ユーザーが明示した範囲で行う。
- 秘密情報や認証情報を、イシュー、PR、スレッドへのメッセージに書かない。
- 日本語の文章は、ユーザーの文章の基準に従う。
