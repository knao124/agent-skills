# Daily Task Plan

カレンダーとGitHubのタスクから、一日の計画の下書きを日報に書く。一日の終わりには、本人が書いた実績とメモをGitHubへ反映する。CodexとClaude Codeで同じ手順を使う。

## 判断の方針

- 下書きとして使う。情報不足のたびに質問せず、先にIssue本文・親子関係・Project・日報原本を読んで判断する。仮の見積もりや判断は必要な箇所に短く添える。
- 日付は指定がなければ日本時間の今日。日付指定にも対応する。一週間の最適化や固定の勤務・休憩ルールを持ち込まない。
- 「計画を作る」と「実績を反映する」は別の操作。計画作成だけの依頼でIssueを作成・完了にしない。実績反映の依頼があれば、根拠のある更新を進める。
- 既に依頼された操作について毎回承認を取り直さない。保存先を特定できない場合や権限不足など、実行に不可欠な点だけを確認する。

## 設定と接続

`~/.config/daily-task-plan/config.json`を読む。設定形式は[references/operations.md](references/operations.md)の「ローカル設定」を参照する。

- 日報URL・文書ID・タブID・アカウント・カレンダーIDはローカル設定に置く。skill、評価データ、コミット、PR本文に実値を含めない。日報やIssue本文に含まれるURLを例としてコピーしない。
- 原本の取得結果や作業用JSONもリポジトリ外の一時ディレクトリに置く。
- Computer Useが使える場合は画面操作を優先する。カレンダーはローカルのカレンダーアプリでもよく、ブラウザに限定しない。DocsとGitHubは利用できるブラウザ画面を使う。[references/computer-use.md](references/computer-use.md)を読む。
- Computer Useが利用できない、または対象サービスを画面から扱えない場合に、`gws`・`gh`へ切り替える。CLIも使えなければ対応する接続ツールを使ってよい。設定済みアカウントを検証し、毎回選び直す質問はしない。
- 初回設定が必要なら会話や既存設定から分かる値を使う。日報URLが未設定なら勝手に別文書を作らず、下書きをチャットに返す。
- 対象カレンダーを一つの時間軸として扱う。カレンダーと会社の対応はローカル設定を使う。会社名・略称・社数はskill内に固定しない。カレンダー自体には書き込まない。

## 計画を作り、日報へ追記する

### 1. 原本と予定を読む

1. 日報Docsをタブ込みで取得し、「日報」タブの直近の日付・箇条書き・追記メモを読む。原本の明示的なフォーマット指定を優先する。
2. 設定したすべてのカレンダーから対象日の予定を取得する。未回答・仮参加も、いったん時間を埋める予定として扱う。不参加・キャンセルは除く。
3. `block`、`ブロック`、`NG枠`など、単なる時間確保の枠は除く。「予定あり」が他社予定の同期コピーと判断できる場合も元予定だけを残す。内容不明の非公開予定まで一律に空き時間にしない。移動・準備の枠は追加しない。
4. 複数カレンダーの同じ会議は一件として扱う。別会議が重なっている場合は短く重複を示し、空き時間を二重に数えない。

### 2. Issueを読み、今日の候補を選ぶ

Projectの列名・フィールド定義と選択肢を確認し、`期限`、`見積もり時間（分）`、`会社`、`タスクの種類`、`Status`とIssue本文・親子関係を読む。会社の表示名は会社フィールドの値をそのまま使う。画面では期限順の一覧やフィルターを使い、見えている数行だけを候補全体だと思い込まない。CLIへ切り替えた場合は[references/project-items.graphql](references/project-items.graphql)で全ページを取得できる。

- 期限超過・当日期限・近い期限を見て、今日進める必要がある作業から選ぶ。関連Issueの受領待ちや前提作業も読む。締切だけで着手不能な作業を詰め込まない。
- 完了・重複終了は候補から除く。`⑨分解済み`の親と子の所要時間を二重計上しない。`③分解が必要`は、必要なら「作業を分解する」という着手可能な単位にする。
- `④単純タスク`は、会社をまたいでも同じ作業・ツールでまとめる。`⑤頭使うタスク`にはまとまった時間を優先する。
- `①委譲タスク`は本人の依頼・確認に要する時間を見込む。Issueにある担当・依頼内容・成果物・期限・確認事項を使い、不明な担当者を創作したり、依頼を送信したりしない。
- 重要度や残り時間が書かれていれば使う。なければIssueの内容から下書きとして見積もる。新しい必須フィールドや確認待ち一覧を増やす必要はない。GitHubの見積もり・期限を推測で更新しない。
- 子Issueの会社が空欄なら親やタイトルと会社フィールドの選択肢を照合して補う。判別できなければ原本の未分類区分に置き、その区分もなければ「未分類」とする。

### 3. 一日の下書きを組む

直近日報の作業時間や休憩を参考に、予定を置いて空き時間へタスクを配置する。日中に組み直す場合は、書き込み済みの実績を残して残り時間を組む。未指定の勤務時間・休憩の質問で止めない。

「今日やること」と「スケジュール」は、GitHubの会社フィールドから取得した区分でまとめる。表示する区分やその数は実データに合わせる。会社別の表示でも、全体を通した時間の重複と所要時間を確認する。収まらないものは「翌日以降に回すタスク」に短く記載する。繰越によって元の期限を自動変更しない。

原本で確認した基本形は次のとおり。日付は見出し、本文はネイティブの箇条書きとし、スケジュールは会社→時間帯→作業の順にする。作業の補足はその作業の子に置く。

```text
YYYY-MM-DD（曜）
- 今日やること
  - <会社フィールドの値>
    - 作業名（15分、M/Dまで） #123
      - 必要な補足
- スケジュール
  - <会社フィールドの値>
    - 09:00-09:30
      - 会議名
    - 09:30-10:30
      - 作業名（60分） #124
  - 翌日以降に回すタスク
    - 作業名 #125
- 振り返り
  -
```

Issue番号には可能なら既存Issueのリンクを付ける。振り返りは本人の記入用に空け、予定を実績として書かない。

### 4. 日報タブの先頭へ入れる

- 新しい日付は日報タブの本文先頭に追加する。別タブや文書末尾に書かない。既存の週次一覧・メモは削らない。
- 同日の記載がある場合は重複した日付ブロックを増やさず、既存の計画部分を必要な範囲で更新する。チェック済み項目・手入力の実績・補足・振り返りは残す。
- 画面操作では「日報」タブと本文の先頭を確認して挿入し、ネイティブの箇条書きと階層を保つ。CLIへ切り替えた場合は、単純な末尾追記ではなくタブIDを指定したDocs APIの`batchUpdate`を使う。[references/operations.md](references/operations.md)の「Docsへの書き込み」を読む。
- 書き込み後に対象部分を取得し、日付・先頭位置・会社→時間帯→作業の階層と既存メモの保存を確認する。

## 日報の実績とメモをGitHubへ反映する

対象日の「今日やること」「スケジュール」「振り返り」を読み、同じ作業に関する記述をまとめる。過去の日報は必要な関連箇所だけ参照する。

1. Issue番号・リンクがあれば、そのIssueを取得する。番号のない作業は、完了済みも含めて既存Issueを検索してから登録先を決める。
2. `[x]`、`[done]`、明示的な完了記述は実績として扱う。ただし「重複」「中止」「今はやらない」などの理由も読む。実施予定の時刻が過ぎただけでは完了にしない。着手や途中までの実績はIn Progress、未実施・繰越だけならTodoを維持する。
3. 既存Issueには対象日付の実績・メモを本文に追記する。作業の下にある補足メモは、対応と箇条書きの階層を保つ。後のメモで前の判断が変わっていれば、経緯が分かる形で最新の内容を反映する。既存本文は残す。
4. カレンダー由来の会議や、その日に発生した未登録の作業も、日報で実施が確認できればIssueにする。作業当日をProjectの期限に設定し、会社と実績に合ったStatusを入れる。完了済みの会議はDone・closedとする。昼食や休憩などは業務Issueにしない。
5. 日報に明示された追加タスクや期限変更も反映する。親が分かればサブIssueとして関連付ける。「翌日以降に回す」だけで繰越日を決めない。子の一部が終わっただけで親全体を完了にしない。
6. Issueのopen/closedとProjectのTodo / In Progress / Doneをそろえる。画面では既存の選択肢を使う。CLIへ切り替えた場合は、その実行時にフィールドID・選択肢IDを取得する。[references/operations.md](references/operations.md)の「GitHubへの反映」を参照する。
7. 同日の反映を再実行したら、同じ日付の実績節を更新する。既存Issue・メモ・追加タスクを重複登録しない。部分失敗や応答不明の書き込みは、現状を取得してから残りを再開する。

GitHubへ書く出典は「YYYY-MM-DDの日報」のような日付だけでよい。ローカル設定のDocs URLやタブIDを転記しない。既存本文にあるリンクはそのまま残す。

## 完了時の返答

何を作成・更新したかを短く伝える。計画なら主な作業と収まらなかったもの、実績反映なら作成・更新したIssueを示す。取得できなかったカレンダーや更新失敗があれば、該当箇所だけ明記する。データが欠けても取得済みの情報で下書きを進め、全件取得・全件反映したと装わない。
