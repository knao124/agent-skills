# 画面操作での進め方

Computer Useが使える場合の優先経路。利用環境が提供する操作ツールの説明を読み、そのAPIと画面に表示された情報を使う。Codex固有のツール名を、Claude Code側にも存在するものとして決め打ちしない。

## カレンダー

ローカルのカレンダーアプリに対象カレンダーがあれば、その表示を使ってよい。Webカレンダーを開き直す必要はない。

1. アプリ一覧・ブラウザタブ一覧から、利用できるカレンダーを確認する。
2. サイドバーのカレンダー名とローカル設定の対応を確認する。複数人の共有カレンダーや個人用カレンダーが同時に表示されていても、設定した対象カレンダーだけを読む。会社の表示名はGitHubの会社フィールドから取得し、カレンダーとの対応はローカル設定で確認する。
3. 対象日を日表示・週表示などで開き、終日欄と必要な時間帯を読む。画面外の早朝・夜の予定も、計画範囲に関係すればスクロールして確認する。
4. 予定のタイトル・開始終了・所属カレンダーを読む。必要なときだけ詳細を開き、参加状態や重複を確認する。色だけで会社を決めない。
5. 時間確保のblock・NG枠と、他社予定の同期コピーを除いて一つの時間軸にまとめる。情報を読めた範囲で下書きを作り、予定を編集したり招待へ回答したりしない。

## GitHub

既存の「タスク一覧」Projectを開き、期限やStatusで候補を絞る。期限・会社・タスクの種類・見積もりが画面にない場合は、表示できるフィールドやIssueの詳細を確認する。候補Issueは本文・親子関係も読む。

実績反映では、番号・リンクがあればそのIssueを開く。番号がない作業は閉じたIssueも含めて検索する。本文の編集、Status・期限・会社の変更、sub-issueの追加には、それぞれ画面の既存機能を使う。対象の会社や日付を見てから保存し、更新後の表示で確認する。

## Google Docs

1. ローカル設定の文書を開き、左のタブ一覧で「日報」を選ぶ。ほかのタブが選択されたまま書き込まない。
2. 直近日付と、その下のネイティブの箇条書き・補足の階層を読む。本文が画像・キャンバスとして表示され、アクセシビリティ情報に文字が出ない場合は、スクリーンショットやアプリ内の検索など、使える画面操作で確認する。
3. 対象日が既にあるかを探す。新しい日なら、本文をフォーカスして文書先頭へ移動し、挿入位置を確認する。同日なら実績やメモを残して計画だけ更新する。
4. 日付見出しと箇条書きを挿入する。書式付き貼り付けが使える場合は、見出しと入れ子のリストを持つHTMLなどを使ってよい。Markdown文字列を貼っただけでネイティブの箇条書きになったとは判断しない。
5. 原本の書式が崩れた箇所は、エディタのスタイル・箇条書き・インデント操作で整える。「会社→時間帯→作業→メモ」の親子関係を目で確認する。
6. 自動保存の表示と挿入部分を確認する。書き込みを確認できない場合は現状を読み、同じブロックを無条件に貼り直さない。

## 代替経路への切り替え

アプリ・ブラウザの操作ツールがない、対象アカウントの画面を開けない、必要な内容を画面から取得できないなど、画面操作で進められない対象だけをCLIへ切り替える。たとえばカレンダーはローカルアプリ、Docsはブラウザ、GitHubは`gh`という組み合わせでもよい。

その場合に[operations.md](operations.md)の該当操作を読む。画面から読めた情報を、念のためという理由だけでCLIでも全件取得し直す必要はない。
