# Requirements Doc Format

## 目的

読み手が実現したいことと動作条件を理解できる形で、機能要件を作成・修正・監査する。GitHub Issueと正式な詳細要件書では、読み手と目的に合わせて形式を選ぶ。

## 共通方針

- ユーザーが別言語を明示しない限り、日本語で回答する。
- 日本語を書く前にwritingを読み込み、下書きと最終稿へ適用する。ユーザーが配置先を指定した場合は、そのwritingを使う。未導入なら同じリポジトリの`skills/writing/SKILL.md`も確認し、読み込めなかった場合は適用済みと報告しない。
- 会話で理解・合意した説明順、具体例、用語を維持する。主張・情報の比重・断定の強さを変えず、不足している条件だけを補う。ユーザーが決めていないことを確定事項として足さない。
- 「誰が・何を・どの条件で・どうするか」が文から分かるようにする。実行者を一覧へ並べただけで、各動作の主語を書いたことにはしない。
- 技術用語や略語は、読み手の判断に必要な範囲で使う。理解済みの説明を抽象的な管理用語へ置き換えない。
- 図・表・章立ては、理解に役立つ場合に使う。ユーザーの箇条書き指定や既存文書の形式を優先する。
- 外部文書やIssueへ保存する前に本文を読み直す。writingを読み込んだことだけで、文章の確認を終えたと扱わない。

## 文書種別を選ぶ

### GitHub Issue・会話での要件整理

ユーザーがIssueへの登録や会話の整理を求めた場合は、この形式を使う。「要件」という語だけで正式な詳細要件書として扱わない。

- 本文は箇条書きで書き、親子関係と並び順で区分を示す。Markdownの見出し・太字・見出し代わりの独立した平文は使わない。コマンド等の原文は子項目のコードブロックとして保持する。
- 必須要件・実装条件・操作例・対象外を分ける。実現したいことは必要に応じて先頭の「目的」に短く書く。該当しない区分は無理に作らない。
  - 必須要件：実装後に何ができれば要件を満たすかを書く。機能のまとまりごとに「要件1：〜できること」のように識別できる形で示し、必要な動作条件だけを子項目に置く。個数は合意内容に合わせ、固定しない。
  - 実装条件：共通APIの利用、権限、データの保管方法など、実現時に守る制約を書く。必須要件の説明と区別するが、任意の参考情報にはしない。未決の設計案は、決定済みの条件と区別する。
  - 操作例：要件の使い方が分かる例を書く。仮のコマンド名・値は仮の例と明示し、例だけで新しい必須機能や設定値を確定しない。
  - 対象外：今回実装しない機能・範囲を書く。実装する機能の権限制約や失敗時の動作を、対象外として省略しない。
- 全文を同じ深さの箇条書きに変えるだけでは整理したと扱わない。読み手が必須要件を先に把握し、各条件がどの要件に関係するか分かるように分類する。
- 同じ条件を概要・用語・機能一覧・処理・出力へ繰り返し書かない。
- 条件・入力・処理・出力、権限、失敗、境界値は、記載漏れを確認する観点として使う。これらを必須の表示見出しにはしない。
- 読み手が動作を理解するために必要な制約、対象外、例を残す。短くするために権限や更新競合などの重要な条件を落とさない。
- 詳細な型一覧・図・改定履歴は一律には追加しない。技術上の補足が必要なら、主な説明を読み終えられる位置へ置く。
- 既存の共通要件は必要な箇所を参照し、Issueごとに全文を複製しない。共通要件の変更が必要なら、変更点を明示する。

例えば、次のように親項目を通常の箇条書きで示す。具体的な機能・個数は対象に合わせる。

```md
- 必須要件
  - 要件1：社員が自分の権限でデータを参照できること。
    - サーバは、本人に許可されたデータだけを返す。
- 実装条件
  - WebとCLIは同じ業務APIを使う。
- 操作例
  - 社員がCLIで案件を検索すると、参照可能な案件が返る。
- 対象外
  - 外部サービスへの自動送信は今回実装しない。
```

### 正式な詳細要件書

ユーザーが詳細要件書やv5標準形式を求めた場合、または対象リポジトリが正式な要件定義書の形式を定めている場合は、[references/detailed-requirements.md](references/detailed-requirements.md)を読む。

- 標準章立て、条件→入力→処理→出力の構成、機能ごとの異常系・境界値を適用する。
- 対象機能に近いサンプルだけを読み、名称・項目を実際の対象へ合わせる。
- `*_spec.md`、非機能要件、概要文書、廃止・統合済みメモには、文書の目的を確認せず詳細要件書の書式を当てはめない。

## 既存資料との整合

- リポジトリへ文書を作成・修正する場合は、既存docsとプロトタイプを確認し、用語とフォルダ構成を合わせる。
- UI/UXと画面遷移はプロトタイプ、業務ロジック・データ仕様・入力検証・エラー時の扱いは要件定義を正とする。判断できない矛盾は明示する。
- 番号付きdocsでは、`001`をプロトタイプ用として扱う。要件定義は通常`docs/002_要件定義書/`または`docs/002_requirements/`に置く。実際の構成がそうなっていない限り、`001`を要件定義、`002`をプロトタイプとして説明しない。

## 最終確認

- ユーザーが求めた文書種別と形式になっているか。
- Issueでは必須要件が識別でき、実装条件・操作例・対象外と混ざっていないか。箇条書きに変えただけで、分類を省略していないか。
- Issue本文にMarkdownの見出しや太字が残っていないか。例の仮の値やコマンドを必須条件として追加していないか。
- 会話で合意した内容、説明順、具体例を保ち、合意済みの説明より読みにくくしていないか。
- 誰が何をするか、実行条件と結果、必要な権限、失敗時と境界値の扱いが分かるか。
- 同じ説明を複数箇所で繰り返していないか。説明していない専門語や不要な見出しを増やしていないか。
- 要件の追加・削除・弱体化がないか。提案と確定事項、実装済みと未実装を混同していないか。
- writingを最終稿へ適用し、強調記号や補足の括弧で説明を済ませていないか。
